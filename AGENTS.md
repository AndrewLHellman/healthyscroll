# CLAUDE.md

Healthy Scroll — a Safari extension for iPhone that skips Instagram Reels (on `instagram.com` in Safari, not the app) that don't match a policy the user wrote in plain English. TikTok in Chrome is the secondary target; YouTube Shorts is later. Read `docs/OVERVIEW.md` first, then `docs/ARCHITECTURE.md` and `docs/DECISION_PIPELINE.md`. The landing page (`apps/web/app/page.tsx`, especially the FAQ) is the current source of truth for product intent; the docs still describe the Chrome/TikTok build and are being brought in line. This file is just operating notes.

## Commands

```bash
pnpm install
pnpm typecheck        # run after every change; all three packages must pass
pnpm build
pnpm dev:web          # Next.js on :3000
pnpm dev:extension    # Vite/CRXJS → apps/extension/dist (Chrome, load unpacked)
pnpm build:safari     # → apps/extension/dist-safari (referenced by the Xcode project)
pnpm dev:safari       # same, rebuilding on save
```

Node >= 22.12 (`.nvmrc`). If corepack complains about a keyid, prefix with `COREPACK_INTEGRITY_KEYS=0`.

### iOS Simulator loop

Xcode 27. Open `apps/ios/Healthy Scroll/Healthy Scroll.xcodeproj`, scheme **Healthy Scroll**, run on an iPhone simulator (⌘R). After each `build:safari`, run again in Xcode so the app is reinstalled. In the simulator: Settings → Apps → Safari → Extensions → Healthy Scroll → on, allow instagram.com and healthyscroll.net (and localhost for local testing). **Every reinstall drops these grants**, and on iPhone Safari may not prompt: if a content script silently doesn't run, grant it again from the page menu (≡ in the address bar) before debugging anything else. Inspect from Mac Safari → Develop → Simulator: the instagram.com page and the extension's background page each have their own console.

- Env for the build goes in `apps/extension/.env.local` (see `.env.example`): `VITE_HS_DEBUG=true` for logs and the `hs:probe`/`hs:skip` hooks; `VITE_API_BASE_URL=http://localhost:3000` to use a local `dev:web` (the simulator can reach the Mac's localhost).
- To check what's actually installed: `xcrun simctl get_app_container booted net.healthyscroll` → `PlugIns/Healthy Scroll Extension.appex/manifest.json`.
- `copy()` in the Web Inspector console doesn't reach the Mac clipboard when attached to the simulator; right-click the result → Copy.

## Layout

- `apps/extension` — MV3 web extension (Vite/CRXJS), two build targets from one codebase (`HS_TARGET`, see `manifest.config.ts` / `vite.config.ts`): **safari** (Instagram only; packaged by `apps/ios`) and **chrome** (TikTok + Instagram, loaded unpacked for development). `background/` is the brain (pipeline), `content/` is eyes and hands only (scrape + skip), `popup/` is one toggle + one textarea, `insights/` is the on-device "your week" page.
- `apps/ios` — Xcode project (generated by `safari-web-extension-converter`) that ships the extension as an iOS app. The app itself is one setup screen (`Resources/Base.lproj/Main.html`). The extension's resources are folder references into `apps/extension/dist-safari`, so rebuild that first.
- `apps/web` — Next.js 16 landing + dashboard + `/connect` (Safari sign-in) + `app/api/evaluate/route.ts` (calls Jev).
- `apps/vision` — Python/FastAPI `POST /describe`: pulls frames from a Reel's DASH manifest or video URL with ffmpeg (range requests, no full download) and has a VLM (`VISION_CAPTIONER`) write a short description, cached per Reel. It decides nothing and never sees a policy; the extension hands the description to Jev. `bench/` compares models on labeled clips. See `apps/vision/README.md`.
- `packages/shared` — types, Jev question schema, thresholds, vision contract, `/connect` protocol. Consumed as raw TS by both apps.

## Rules of the codebase

- **All platform DOM knowledge lives in one adapter per site under `apps/extension/src/content/`** (`instagram.ts` for Reels, `tiktok.ts` for TikTok). Nowhere else. Prefer stable hooks (`data-e2e` on TikTok, `aria-label`/roles on Instagram) over class names.
- **Instagram Reels:** active Reel + skip live in `content/instagram.ts` (entry `content/instagramMain.ts`). Reel media (DASH manifest, video URL, poster, caption) comes from Instagram's API responses via the main-world hook `public/instagram-hook.js` (plain JS, appended to the built manifest by `vite.config.ts`; it can't import anything). Every Reel's `<video>.src` is also a direct progressive MP4, including upcoming ones — a fallback if the hook breaks.
- **The content script never makes decisions.** TikTok: reports `VIDEO_CHANGED`, executes `SKIP_VIDEO`; judgement in `background/orchestrator.ts`. Instagram: reports `REELS_DISCOVERED` / `REEL_ACTIVE`, executes `SKIP_REEL`; judgement in `background/reels.ts`, and **every decision is Jev's**: for each Reel as it loads, Jev on the text and vision `/describe` run in parallel; a text-only skip acts at once, then Jev runs again on text + description and that answer is final. The vision service only turns video into text. One skip per Reel.
- **The extension never holds the AI Gateway key.** Jev is only called from `apps/web/lib/jev.ts`.
- **Auth is Supabase + Google, session in the background** (`background/auth.ts`, `chrome.storage.local`). Sign-in is required to be filtered: `/api/evaluate` and `/describe` reject calls without a Supabase bearer token (verified in `apps/web/lib/supabase.ts` / `apps/vision/vision/auth.py`). Chrome signs in with `chrome.identity`; its extension ID is pinned by `key` in the manifest (private key `apps/extension/key.pem`, gitignored). **Safari has no `chrome.identity`**: "Sign in" opens `healthyscroll.net/connect`, which signs in with its own Supabase client (separate `storageKey`, no auto-refresh) and `content/connect.ts` hands that session to the background (`AUTH_HANDOFF`), then deletes it from the page. Never share the website's session with the extension: two clients rotating one refresh token get it revoked. Protocol: `packages/shared/src/connect.ts`. **The website never uses Supabase's hosted OAuth page** (it would show `<project>.supabase.co` on Google's consent screen): `apps/web/lib/googleSignIn.ts` redirects to Google itself (`response_type=id_token`, hashed nonce), Google returns to the same path with `#id_token=`, and `signInWithIdToken` turns it into a session. Google client ID is `GOOGLE_CLIENT_ID` in `packages/shared` (must match Supabase's Google provider); every return path (`/dashboard`, `/connect`) must be an Authorized redirect URI on that Google client, per origin (incl. `http://localhost:3000` for dev). Only the Chrome dev path (`background/auth.ts`) still goes through Supabase's OAuth URL and its Redirect URLs allow list.
- **Database is Supabase Postgres with RLS** (`supabase/migrations/`). Tables: `policies` (one row per user), `skips`, and `feed_days` (daily watch totals per topic). The extension syncs in `background/sync.ts` only; DB calls are best-effort and must never block or trigger a skip.
- **Watch tally ("Your week") is daily totals, never per-Reel records.** The Instagram content script times each Reel off its existing 250 ms active-Reel check (visible time only, capped at 3 min, swipe-throughs under 1 s ignored) and sends batches (`REELS_WATCHED`). `background/tally.ts` adds them to per-day, per-category totals in `chrome.storage.local`; the category is Jev's most confident `category` answer across the text and text+description passes (`reels.ts`). Signed-in users' totals are upserted to `feed_days`; which Reels were watched never leaves the phone. Shapes and `summarizeDays()` in `packages/shared/src/feed.ts` / `insights.ts`. Debug: `dispatchEvent(new Event("hs:tally"))`.
- **The extension never uploads the user's screen.** Visual analysis runs server-side in `apps/vision` on the Reel's own public CDN video, fetched from the manifest/URL the extension sends. No screenshots; frames are described and discarded (descriptions are cached per Reel, not per user, and no policy is sent to the vision service). Of the watch tally ("your week"), only daily totals per topic leave the phone, and only for signed-in users. `background/moondreamClient.ts` → `localhost:2020` is the legacy Chrome/TikTok path.
- **Audio is the last resort, and it costs money.** Only when Jev is still unsure (0.2 < p < 0.8) after text + description, and only for the Reel on screen, `reels.ts` asks the vision service's `POST /transcribe` for what's said: the server takes the first 30 s of the Reel's own audio track (DASH manifest) to ElevenLabs Scribe v2, caches the transcript per Reel, and Jev decides on text + description + `transcript` (stage `audio`). Reels with a licensed song (`audioKind: "music"`) are skipped. The server caps new transcriptions per user and per day (`TRANSCRIBE_*`); any failure keeps the earlier answer. Never call it for every Reel or from prefetch.
- **Never skip on error.** If Jev/vision/API fails, log and leave the Reel alone. Only confident matches (`THRESHOLDS.skip`) skip; the middle band gets a second look, never a guess.
- Cross-context message types are defined once in `apps/extension/src/lib/messages.ts`.
- Anything shared between extension and web (types, Jev schema, thresholds) goes in `packages/shared`.
- **Safari on iOS is the constraint.** No `chrome.tabs.captureVisibleTab`, no `chrome.identity`, no `localhost` in the product, and the background can be unloaded anytime (it's a non-persistent background page on Safari). Anything that only works in desktop Chrome is dev tooling, not product.
- **Safari can't run CRXJS's ES-module loaders.** Its `type: module` service worker never starts (with an empty console, not an error) and content scripts loaded via `import()` fail. So for the Safari target the background and every content script are built as classic IIFEs by `postBuildScripts()` in `vite.config.ts` and added to the built manifest there — a new Safari content script goes there, not in `manifest.config.ts`. Files land in `dist-safari/assets/`, which the Xcode project references as a folder; a new top-level file would also need adding to the Xcode project. Safari match patterns can't contain a port (`http://localhost:3000/*` is silently ignored); use `http://localhost/*`, which matches every port.
- UI is minimal by design. Don't add settings, stats, or onboarding without being asked. The popup is one toggle, one text box, one line about today.

## Deploy

Pushing to `main` builds `apps/web/Dockerfile` and `apps/vision/Dockerfile`, pushes them to `ghcr.io/andrewlhellman/healthyscroll-{web,vision}`, and restarts both on the server via `deploy/docker-compose.yml` (`.github/workflows/deploy.yml`). On the server: `/srv/healthyscroll/{docker-compose.yml,.env}`; web on `127.0.0.1:3001` behind nginx site `healthyscroll.net`, vision on `127.0.0.1:8000` behind `vision.healthyscroll.net` (`deploy/nginx/`, installed by hand). Secrets go in the server's `.env`, never in the repo. The server has no GPU, so vision describes Reels through the AI Gateway (`VISION_CAPTIONER=gemini-2.5-flash-lite` in the compose file; the gateway account is free tier, which blocks the 3.x Flash-Lite models).

## External APIs (verified 2026-09-25)

- Jev: `experimental_evaluate({ model: "typesafe-ai/jev", state, questions })` from `ai@7`. Boolean answers → `result.answers.<q>.probability`. Details in `docs/JEV.md`.
- Moondream REST (legacy Chrome path): `POST /v1/caption|query` with `{ image_url: <data URL> }` against Moondream Station on `localhost:2020`. Details in `docs/MOONDREAM.md`.
- Instagram CDN (checked 2026-09-26): Reel MP4 URLs are signed (`oe` = expiry, ~32 h), need no cookies, support range requests, and send `Access-Control-Allow-Origin: *`.
